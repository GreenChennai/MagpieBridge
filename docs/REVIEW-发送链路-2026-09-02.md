审查日期：2026-09-02

重点：**① 发送前目标校验 ② 重复发消息 ③ 可优化点**

## TL;DR

| 等级        | 数量 | 一句话                               |
| --------- | -- | --------------------------------- |
| **P0 致命** | 5  | 会把消息发错人 / 同一条消息重复发，且**没有任何一层能拦住** |

## 一、P0 —— 会发错人 / 重复发

### P0-1 【发错群/人】`find_contact_by_name` 双向子串匹配，命中谁全看运气

`magpie/core/ocr.py:336-339`

```python
for item in items:
    item_name = item.name.strip().lower()
    if target_lower in item_name or item_name in target_lower:   # ← 双向子串
        return item                                              # ← 返回"第一个命中"
```

`items` 按 `y_position`（列表从上到下）排序，所以命中的是**列表里最靠上的那个模糊匹配项**：

| 目标        | 列表里存在         | 结果                            |
| --------- | ------------- | ----------------------------- |
| `客户群`     | `客户群2`、`客户群A` | `客户群` in `客户群2` → **点进 客户群2** |
| `张三`      | `张三丰`         | **点进 张三丰**                    |
| `安信德&创客龙` | OCR 只截出 `安信德` | `安信德` in 目标 → **点进这个残缺行**     |

这是"发错群"的直接根因，且后面的校验层**同样松**（见 P0-2），两道防线一起失效。

### P0-2 【发错群/人】`_title_matches` 子串 + 0.6 相似度，等于没有校验

`magpie/core/wechat_adapter_4x.py:184-195`

```python
if tl == tt or tt in tl or tl in tt:            # 子串 → "客户群" 通过 "客户群2"
    return True
return difflib.SequenceMatcher(None, tt, tl).ratio() >= 0.6   # 0.6 对中文短名几乎无区分度
```

`"张三"` vs `"张五"` = 0.5 能挡住，但 `"客户群"` vs `"客户群2"` = 0.857 直接通过。  
**发送前的"我确认过是这个人"这一步，实际上是纸糊的。**

### P0-3 【无发送前最终校验】从"找到人"到"按 Enter"之间有 3~6 秒无人看守

`magpie/core/ui_engine.py:130-138` + `wechat_adapter_4x.py:622-647`

```
search_contact() 校验通过
   ↓  sync_delay()            ~0.2-1.5s
   ↓  send_text() → click 输入框   0.3s
   ↓  think_pause()           ~1.2±0.5s（最坏 2.2s）
   ↓  _ensure_input_content() 逐字输入 / 粘贴  1-6s
   ↓  _send_message() → Enter      ← 此时完全没有再确认"当前打开的是谁"
```

在这 3~6 秒里，用户手动点一下微信、微信后台同步把列表重排、上一条操作的异步渲染延迟到这一步才生效 —— **都会让 Enter 打在错误的会话上**。  
`_send_message()` 甚至写死了 `return True`（注释原文："After sending, the message is sent regardless of what pixel detection says"），连事后验证都放弃了。

**这是你提的"发送前检测当前群/人"必须补的位置。**

### P0-4 【重复发送 · 根因 1】去重键不一致 —— 同一条消息被两个桶各记一次

`magpie/monitor/listener.py`

去重集合是 `self._processed: dict[str, set[str]]`，**键 = 会话名**。但同一个会话在不同代码路径下名字来源不同：

| 调用点                            | 会话名来源                              | 示例值                      |
| ------------------------------ | ---------------------------------- | ------------------------ |
| `_process_current_chat()` L388 | `adapter._chat_title()`（聊天区标题 OCR） | `安信德&创客龙` / `安信德&创客龙(3)` |
| `_process_unread()` L544       | `item.name`（聊天列表 OCR）              | `安信德&创客龙`                |
| `_monitor_session()` L594      | `self._sessions` 的 key（上面两个都可能写进去） | 两种都有                     |

OCR 对全角/半角 `＆` vs `&`、尾部群人数 `(12)`、长名截断的识别**每次都可能不同**。  
一旦两个名字字符串不完全相等 → **`self._processed` 出现两个桶 → 同一条消息被提取两次 → `_schedule_dispatch` 派发两次 → 插件回复两次 → 群里看到两条一模一样的消息。**

同时 `_sessions` 也会被同一个群拆成两个 `ActiveSession`，`_current_session` 判断失效，`_monitor_session` 反复误判"需要切换会话" → 又多一次搜索+点击。

### P0-5 【重复发送 · 根因 2】`_process_unread` 只派发"最后一页"的消息（变量被覆盖）

`magpie/monitor/listener.py:540-557`

```python
for p in range(pages):                       # scroll_pages 默认 3
    texts, region = self._ocr_chat_area()
    new_msgs = self._extract_messages(...)   # ← 每轮覆盖
    for m in new_msgs:
        self._messages.append(m)
        self._store.save_message(...)
    collected += len(new_msgs)
    if p < pages - 1:
        self._scroll_chat_down()

self._schedule_dispatch(new_msgs)            # ← 用的是"最后一页"的 new_msgs，不是累计值
```

- 若回复在第 1 页被读到、第 3 页没有新内容 → `new_msgs == []` → **回复永远发不出去**（漏发）。
- 若最后一页因为滚动回环又读到了同一条、且键与前面不一致（P0-4）→ **重复派发**。
- 正确做法：累计 `collected_msgs`，循环外统一派发。

### P0-6 【重复发送 · 根因 3】插件受理确认是"全员广播"式发送

`plugins/leads_forwarder/__init__.py:1002-1033`

```python
matched_pends = [p for p in _pending_leads if p["group"] ... and contact in p.get("group","")]
if not matched_pends:
    matched_pends = [(pid,p) for pid,p in _pending_leads.items() if p["status"]=="pending"]   # ← 兜底：全库
if is_accept:
    for pid, pending in matched_pends:          # ← 有几条待受理就发几条确认
        await engine.send_text(group, confirm_msg)
```

两个问题叠加：

1. `contact in p.get("group","")` 是**反向子串**（contact 是完整的群名，p["group"] 也是群名，OCR 噪声导致不匹配）→ 一旦一个都匹配不上，就**退回"全库所有待受理线索"** → 给**所有群**各发一条"✅ X 已记录承接"。
2. 匹配上时，`matched_pends` 可能有多条 → 循环里连发 N 条。

再叠加上 P0-4（同一条回复被派发两次），群里就是 **2 × N 条重复确认**。

### P0-7 【重复发送 · 根因 4】OneBot 层谎报成功 → 上游重试 → 重复发

`magpie/onebot/v11_http.py:109-131` 与 `v11_ws.py:99-116`

```python
await self.engine.send_text(contact, message)      # ← 返回值直接丢弃
return {"message_id": int(time.time() * 1000)}     # ← 永远成功
```

`engine.send_text()` 返回 `False`（没找到联系人 / 输入框验证失败）时，OneBot 依然返回 `message_id`。  
浏览器插件 / 上游系统看到成功或超时后**按失败重试** → 同一条线索再发一遍。  
**"没发出去"和"发出去了"在接口层无法区分，是重复发的放大器。**

---

### P0-8 【重复发送 · 根因 5】发送层零幂等

`magpie/core/op_queue.py` + `ui_engine.py`

- `OperationQueue` 只做串行，**没有去重、没有幂等键、没有超时、没有队列上限**。
- 同一个 `(kind, target, detail)` 在几秒内被提交两次（Web 双击残留、OneBot 重试、插件超时转发 + 人工转单并发、阻塞队列 flush 与实时发送并发）就会真发两次。
- `_run()` 里 worker 被 cancel 或异常退出时，`fut` **永远不会被 set_result/set_exception** → `submit()` 的 `await asyncio.shield(fut)` **永久挂起**，调用方卡死（`_queue.task_done()` 也从未调用）。

## 二、P1 —— 严重缺陷

### P1-1 【@ 功能 100% 失效】`re` 未导入导致 `NameError` 被静默吞掉

`magpie/core/wechat_adapter_4x.py:813`

```python
if re.match(r"^\d{1,2}:\d{2}$", line):   # ← 本文件顶部没有 import re
```

文件顶部只有 `import ctypes/difflib/io/logging/random/time`，`re` 只在 `_title_matches()` 里 `import re as _re`（局部）。  
`_try_pick_at_member()` 里的裸 `re` → `NameError` → 被 L838 的 `except Exception` 吞掉 → 恒返回 `(False, -1, 0.0)`。

后果链：

```
_try_pick_at_member 恒 False
  → _try_search_and_pick 恒 False
  → _type_at_suffix 恒 False
  → _type_at_and_pick 走兜底：if _at_candidate_open(): _send_enter()
      → 盲按 Enter 选中候选面板第一条（可能不是目标成员）
  → send_at 再按一次 Enter 发送
```

**@ 的人可能一直是错的，且日志里只看到"弹窗选择=False"，很难发现。**

### P1-2 【输入框校验形同虚设】`dark > 3` 阈值过低

`wechat_adapter_4x.py:589-597`：在 580×40（约 23000 像素）的区域里只要 >3 个非白像素就算"有内容"。  
输入框边框、表情图标、光标、上一条消息的残影都远超 3 个 → **恒为 True**。  
于是"粘贴失败 → 重试"的重试逻辑永远不会触发，空内容直接 Enter（发送空消息或什么都不发），而 `send_text` 依然返回 True。

### P1-3 【发送结果不可信】`_send_message()` 无验证、恒 True

`wechat_adapter_4x.py:499-508`：只按 Enter + `sleep(0.8)` 就 `return True`。  
`_send_button_active()` / `_click_send_button()`（L510-558）**写了但从未被调用** —— 发送按钮变灰检测这套已实现的验证完全没接上。

### P1-4 `get_current_chat_name()` 恒返回 None

`wechat_adapter_4x.py:900-901` → `engine.get_status()["current_chat"]` 永远是 `null`。  
Web 后台 / API 无法展示"当前正在对谁操作"，排障时缺少最关键的状态位。

### P1-5 `_get_screenshot()` 异常路径泄漏 GDI 句柄

`wechat_adapter_4x.py:105-135`：只在正常路径 `DeleteObject/DeleteDC/ReleaseDC`。  
`PrintWindow` 或 `GetDIBits` 抛异常 → `bmp` / `mfcDC` / `hdc` 全部泄漏。  
这是 7×24 长跑程序，泄漏累积到 10000 句柄后 Windows 会拒绝分配 → 截图开始返回黑图 → OCR 全乱 → 可能连锁导致误判会话。  
（`admin/command_handler.py:155-195` 有同样问题的副本）

### P1-6 CORS 全开 + 凭证，本地管理接口可被任意网页调用

`magpie/web_server.py:105-111`

```python
allow_origins=["*"], allow_credentials=True, allow_methods=["*"]
```

监听 127.0.0.1:8080，但**任何你在浏览器里打开的网页**都能 `fetch("http://127.0.0.1:8080/api/send/text")` 以你的微信身份发消息（CSRF）。  
应改为限制 `http://127.0.0.1:8080` / `http://localhost:8080` 白名单，并对写操作加 token。

### P1-7 OneBot 未鉴权时完全裸奔

`v11_http.py:42-46`：`token` 为空时 `_check_auth` 直接 `return True`。  
默认 `config.json` 的 `access_token` 就是空。同机任何进程都能调用 `send_group_msg`。
