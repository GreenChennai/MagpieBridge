# ADR-0002: 统一数据层 = SQLite(WAL) 单库 + 人读 JSON 配置 + CSV 导出

日期:2026-09-07
状态:已接受

## 背景

旧版数据割裂:发出的消息进 SQLite(`messages.db`),收到的消息进**另一套**
按联系人的 CSV(`~/MsgPushWechat/data/messages/*.csv`),Web 后台只能看到
发出的一半。CSV 追加写还会被 Excel 独占锁卡死(用户打开看数据时,程序写不进)。

需求:高性能、高效;同时用户要能**简单地**打开查看/修改数据,且查看时
程序仍能正常保存/同步。

## 决策

按"谁写谁读"分三类存储:

1. **机器高频写的流水** → 单个 SQLite 库 `data/magpie.db`,WAL 模式:
   - 收发消息同表(`messages`,direction 区分),Web 后台一份数据源;
   - WAL 允许"程序在写、任何人随时读",`busy_timeout` 兜底;
   - 用户**不直接编辑 .db**(修数走 Web 后台,或导出 CSV 改完再导回的功能后续再加)。
2. **人手编辑的配置** → JSON 文件(`config.json`、`plugins/config/*.json`):
   保持 Notepad 可改,保存后热生效。
3. **用户要看/留档的数据** → Web 后台一键导出 Excel 友好 CSV(UTF-8 BOM)
   到 `data/exports/`;插件(LeadsLinker)的线索台账保持按月 CSV 追加,
   写入遇 Excel 锁时进待写队列稍后重试,不丢数据。

## 备选与否决

- **全 JSON/CSV**:人读最爽,但消息流水高频追加时性能差、无索引、并发读写易损坏。
- **全 SQLite(配置也入库)**:性能最好,但违背"用户必须能简单地打开改配置"。
- **黑遮罩层/虚拟桌面**:见 ADR-0003,与存储无关但同期否决。

## 后果

- 旧 CSV(如有)与旧 `messages.db` 启动时一次性迁移进新库,迁移后原文件保留不动。
- 写路径统一走独立写线程 + 队列,调用方永不阻塞在磁盘上。
